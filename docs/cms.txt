GCOM CMS operations

Status and authority

This migration is prepared for staging verification. SANITY_PUBLICATION_ENABLED
must remain unset or false, and the Sanity publication webhook must remain
disabled, until staging Studio, published-content builds and the human review
have passed and the owner explicitly approves production publication.
Sanity credentials are stored outside source in a mode-600 secret file. Live
staging was seeded and built. Published reads, draft exclusion, seed rerun,
anonymous write denial and secret scans passed. Human Studio review, collaborator
role checks and production approval remain pending. Fixture checks alone do not
satisfy the staging gate.
No remote webhook, repository setting, privacy change, deployment enablement or
push is part of local setup. The existing repository is public: never commit
credentials or treat repository privacy as a secret boundary.

Publishing in Studio changes Sanity content. It does not confirm a successful
website deployment. A delivered webhook only queues a workflow. A successful
Pages deploy job and a check of the live four routes establish publication.
CMS validation, Studio checks, browser checks or deployment failures preserve
the existing Pages deployment. A failed release never substitutes fixture data.

Install and local verification

From the repository root, using Node 22:
  npm ci
  npm ci --prefix sanity
  npm ci --prefix editor
  npx playwright install --with-deps chromium
  CONTENT_SOURCE=fixture npm run build
  npm test
  npm test --prefix editor
  npx tsx --test sanity/*.test.ts
  npm run format:check
  npm run test:browser

Fixture mode is for offline development and tests. CI rejects fixture syncs.
content/fixture.json is the local reference; src/generated/site-content.json is
the validated build snapshot. Never edit generated output as the content source.

The root scripts are:
  npm run sync:content: validate fixture or published Sanity content, then write
    the snapshot atomically; CONTENT_SOURCE selects sanity or fixture.
  npm run build: sync content, then run build:snapshot.
  npm run build:snapshot: typecheck, generate HTML, Vite build and prerender from
    the snapshot already on disk, without another CMS fetch.
  npm run build:release: require Sanity content for a release build.
  npm run dev: sync content before local development.
  npm run seed:content: seed missing singleton documents in a non-production
    dataset; existing published documents and drafts are skipped.
  npm run sync:events: import Luma using settings.calendarUrl in the snapshot.
  npm run test:browser: serve the final dist on 0.0.0.0 at an ephemeral port;
    honor SITE_BASE; check four routes at desktop and mobile sizes, prerender,
    assets, fonts.ready, loaded Nunito/Pixelify Sans, overflow, serious/critical
    Axe findings, browser/hydration errors, absence of browser CMS requests,
    keyboard menu/Escape focus, reduced motion and contact draft preservation.
    Isolated Vite contact fixtures compile the same snapshot with missing and
    mocked endpoints (400/413/429/500/200 with ok:false, malformed JSON and
    a network failure); they never refetch CMS, alter dist or submit real messages.

Sanity project, datasets and access

An owner creates the Sanity project and explicit staging and production datasets
in https://www.sanity.io/manage. Prefer private datasets; changing an existing
dataset's visibility requires owner approval. The project ID is wtzkb2rs;
use the explicit staging or production dataset. Install Studio dependencies separately under sanity/.

Invite committee users by account through Sanity Manage project Members, using
the sign-in method they will actually use. Give editors the Editor role when
available, reviewers Viewer, and only the technical owner Administrator or
Developer as needed. Editor, Developer and Contributor availability depends on
the Sanity plan. If the plan lacks a suitable editing role, resolve access with
the owner before inviting people; do not silently give all editors admin access.
Contributor can draft but cannot publish. Viewer cannot edit. Remove departing
committee access in Sanity. Studio's singleton UI is not an authorization layer;
Sanity project roles and dataset permissions enforce access.

Studio has six fixed documents, with identical _id and _type:
  settings, navigation, home, about, team, contact
Duplicate and delete actions are hidden and creation templates are restricted.
Publish all six to staging; drafts are never used by the website build. Local
Studio login uses each member's Sanity account, not a shared write token.

Use SANITY_STUDIO_PROJECT_ID and SANITY_STUDIO_DATASET for Studio. Seeding uses
SANITY_PROJECT_ID, SANITY_DATASET and SANITY_WRITE_TOKEN.
Use SANITY_WRITE_TOKEN only in the server-side seed process; store it in a
mode-600 secret file outside the repository and inject it without printing it.
The seed refuses production and skips existing published and draft singletons.
It uploads approved local artwork and existing public roster portraits, retains
alternative text, then creates missing documents with createIfNotExists.

Set the project and dataset explicitly for subsequent commands:
  export SANITY_PROJECT_ID=wtzkb2rs
  export SANITY_DATASET=staging
Load the confirmed mode-600 token file without printing its contents:
  read -r SANITY_WRITE_TOKEN < "$HOME/.claude/.secrets/gcom-sanity-token"

Seed and verify Studio:

  SANITY_STUDIO_PROJECT_ID="$SANITY_PROJECT_ID" SANITY_STUDIO_DATASET=staging npm run dev --prefix sanity

Field ownership map

Every fixture field is managed by its owning singleton below. Dot notation names
fields; [] means each ordered array entry. Content owns text, links, image/alt
values and ordering. CSS, route layout, decorative symbols and motion mechanics
remain source-owned. Image src/alt fixture objects become Sanity image assets
with alt, then validated media URLs in the snapshot. Empty alt is intentional
for decoration; meaningful photos/social images need descriptive alternative
text. Use approved artwork, retain attribution, and obtain consent for portraits.

  fullName -> generated application-name metadata.

  contactEmail -> ContactForm direct-email fallback.
  calendarUrl -> Events calendar link and Luma importer destination.

    quest-card decoration. Other page images have their own page fields.

Environment and trust boundaries

Server-side website sync reads SANITY_PROJECT_ID, SANITY_DATASET and optional
SANITY_READ_TOKEN. A private dataset requires a least-privilege read token.
These are not VITE_ or SANITY_STUDIO_ tokens. Read/write tokens never enter
website JavaScript, Studio bundles, HTML, snapshots, logs or vault notes.
Published CMS text/media and public profile fields do enter the static site;
do not store contact submissions or private committee details there. Sanity
image CDN assets are public-delivery resources, not a place for secret uploads.

Studio project/dataset IDs are public routing identifiers. Studio build receives
only SANITY_STUDIO_PROJECT_ID/DATASET, never the read/write tokens. Website browser
code receives VITE_CONTACT_ENDPOINT, a public contact-service URL, never backend
mail-provider or publishing credentials. Contact service recipient/security
configuration remains in the existing editor backend's protected environment.
Retain the existing contact/editor service until live Sanity has been verified;
do not remove its authentication, data or deployment during this migration.
The former public/data/team.json is seed/rollback input; Sanity team.members owns
the public website roster after migration. Avoid treating both as live editors.

GitHub Actions repository variables to review:
  SANITY_PROJECT_ID: wtzkb2rs.
  SANITY_DATASET: production for automatic release runs.
  SANITY_PUBLICATION_ENABLED: unset or false until staging passes and approval.
  SITE_ORIGIN: https://gcom.techtom.tech unless explicitly changed.
  SITE_BASE: /, or an absolute directory path ending in /.
  CONTACT_ENDPOINT: approved contact-service endpoint or blank for email fallback.
GitHub Actions secrets:
  SANITY_READ_TOKEN: read-only access needed by the chosen dataset.
  LUMA_ICAL_URL: private calendar subscription feed.
Legacy LUMA_CALENDAR_URL and CLUB_CONTACT_EMAIL no longer own website content;
settings.calendarUrl/contactEmail in the validated CMS snapshot do.

The workflow preserves push, manual and half-hour cron triggers. Automatic runs
skip while migration publication is disabled. A human may explicitly validate
staging without deploying:
  gh workflow run pages.yml --repo kitsunies/gcom-website --ref main --field dataset=staging
  gh run list --repo kitsunies/gcom-website --workflow pages.yml
  gh run view RUN_ID --repo kitsunies/gcom-website --log-failed

Manual dataset defaults to production so the exact webhook body below works.
Before approval, even manual production validation cannot deploy. After approval,
a manual production run on main can deploy, so use staging for continued tests.
CI always uses CONTENT_SOURCE=sanity, fetches CMS once before event sync, checks
format/root and retained editor/contact tests and Studio schema/seed
tests/typecheck/build, builds that snapshot, then runs browsers
before upload/deploy. Luma import failures use the last valid cached snapshot;
without a dated previous snapshot they fail closed. Cache eviction can therefore
block a release during a Luma outage. CMS failures do not fall back to fixtures.
Deploy requires all three: SANITY_PUBLICATION_ENABLED == 'true', fixed
refs/heads/main, and the selected dataset exactly production. Staging never
deploys. The migration does not turn any repository variable on by itself.

Reviewable publication webhook configuration, disabled until approval

Create this only after staging verification and explicit owner approval. Review
all values first; this file contains no token and creates nothing remotely.
In Sanity Manage project API > Webhooks:
  Name: GCOM production Pages publication
  Dataset: production
  Enabled: false initially; enable only after approval
  Trigger on: create, update, delete
  Trigger on drafts: false
  Trigger on versions: false
  HTTP method: POST
  URL: https://api.github.com/repos/kitsunies/gcom-website/actions/workflows/pages.yml/dispatches
  Filter (GROQ, including deletion/unpublish via before()):
    !((coalesce(after()._id, before()._id)) in path("drafts.**")) && coalesce(after()._id, before()._id) in ["settings", "navigation", "home", "about", "team", "contact"]
  Projection (GROQ): {"ref": "main"}
  Resulting JSON body: {"ref":"main"}
  HTTP headers:
    Content-Type: application/json
    Accept: application/vnd.github+json
    Authorization: Bearer <fine-grained repository-only PAT>
    X-GitHub-Api-Version: 2026-03-10

Create a fine-grained GitHub PAT owned by the responsible repository maintainer,
restricted to kitsunies/gcom-website with Actions: write and a managed expiry.
Store its value only in the Sanity webhook Authorization header, never source,
Studio environment, build snapshot or a shareable webhook configuration URL.
Do not add workflow body parameters unsupported by workflow_dispatch. Omitting
inputs uses the workflow's default production dataset; ref is fixed main.
Webhook deletion/unpublish queues a build that fails if a required singleton is
missing, preserving the live release. Restore and publish that singleton before
retrying. Use Sanity attempts/message logs and GitHub Actions to trace failures.
Rotate/revoke the PAT when ownership changes. A successful dispatch response,
usually 204, proves acceptance only, not build or Pages deployment success.

Backup, promotion and recovery

Use authenticated Sanity CLI login from sanity/ with an authorized maintainer.
Keep exports outside this public repository in protected storage, including
assets and drafts. The CLI may exclude assets returning 401/403/404; inspect the
export log, retain a known complete backup and verify restoration before relying
on an export. Do not use --no-assets for recoverable image backups.
Example after creating a mode-700 directory at $HOME/.claude/backups/gcom:
  cd sanity
  npx sanity login
  SANITY_STUDIO_PROJECT_ID="$SANITY_PROJECT_ID" SANITY_STUDIO_DATASET=staging npx sanity datasets export staging "$HOME/.claude/backups/gcom/staging.tar.gz"
  SANITY_STUDIO_PROJECT_ID="$SANITY_PROJECT_ID" SANITY_STUDIO_DATASET=production npx sanity datasets export production "$HOME/.claude/backups/gcom/production-before.tar.gz"

Restore into a separate non-production dataset first:
  SANITY_STUDIO_PROJECT_ID="$SANITY_PROJECT_ID" SANITY_STUDIO_DATASET=staging npx sanity datasets create recovery --visibility private
  SANITY_STUDIO_PROJECT_ID="$SANITY_PROJECT_ID" SANITY_STUDIO_DATASET=staging npx sanity datasets import "$HOME/.claude/backups/gcom/staging.tar.gz" recovery
Then run Studio and root CONTENT_SOURCE=sanity sync/build/browser verification
against recovery. Do not delete the source dataset or assume imports remove extra
documents. --missing preserves existing IDs; --replace replaces matching IDs.
For production promotion/restoration, first export current production, review
the selected backup and obtain explicit approval to replace its documents:
  SANITY_STUDIO_PROJECT_ID="$SANITY_PROJECT_ID" SANITY_STUDIO_DATASET=production npx sanity datasets import "$HOME/.claude/backups/gcom/staging.tar.gz" production --replace
The seed script intentionally cannot seed production. Promotion is a reviewed
export/import operation, followed by all production build checks.

If publication fails, inspect the failed Actions job, keep the current Pages
release, fix missing/invalid published fields or read permissions, and dispatch
again. If Luma fails without a cache, restore a known valid dated snapshot or
wait for Luma recovery. If a bad release went live, disable publication/webhook,
restore the approved published CMS content from a verified backup, validate
staging, then obtain approval to release the restored production snapshot.
Do not overwrite an old valid snapshot with malformed data or delete datasets.
Keep the old editor/contact deployment until live Sanity and contact behavior
are verified; preserve its existing backup/restore process during the transition.
